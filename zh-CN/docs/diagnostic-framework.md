# 通用支付诊断框架

当AI/SaaS订阅付款失败，而平台专属清单又不能马上解释原因时，用这套框架继续排。

## 1. 先确认失败的到底是什么交易

先分清楚：

- 第一次订阅付款
- 续费
- 未支付invoice
- workspace/team账单
- API账单
- 应用商店账单
- 网页checkout

不要把这些混在一起。同一个产品，因为订阅入口不同，背后可能就是不同的billing系统。

## 2. 改任何东西之前，先保存证据

至少记录：

- 完整报错
- UTC时间
- 首次付款还是续费
- web / app-store / API / workspace中的哪条付款路径
- invoice或transaction ID（如果有）
- 有没有出现身份验证
- 银行/发卡方有没有看到authorization授权请求

截图很有用，但公开分享前要打码卡号、地址、证件信息和账号密钥。

## 3. 最关键的分叉：发卡方有没有看到authorization

### 发卡方看到了授权请求

说明付款请求至少已经走到了卡网络/发卡方这一层。

重点检查：

- 可用余额
- 税费或临时预授权空间
- 卡片、单日或外币限额
- 线上付款设置
- 国际付款设置
- 循环付款设置
- 卡片状态和有效期
- 发卡方安全控制
- 3D Secure或其他验证
- 账单姓名、地址、邮编是否一致

如果银行给出了明确decline reason，把它保存下来。

### 发卡方完全没看到授权请求

没有证据时，不要把它直接叫“银行拒付”。

问题可能发生得更早，例如：

- billing route不匹配
- 未付invoice或billing profile状态
- workspace/账号归属状态
- 账号资格
- 地区、地址和卡片资料一致性
- 卡类型/BIN资格
- 商户侧风控
- checkout/session失败

这个区别很重要，因为如果问题根本没走到银行，反复给银行打电话或者连续换卡，大概率都没碰到真正的问题。

## 4. 一次只改一个变量

不要同时改这些东西：

- 卡
- 账单地址
- 账号
- 地区
- 设备/浏览器
- 网络

五个变量一起换，下一次即使成功，你也几乎什么都没学到。

更干净的排法是：

1. 先保存失败案例。
2. 修正明显的账单/invoice问题。
3. 只有在确实有东西发生变化后，再重试。
4. 如果要测试另一种付款方式，其余环境尽量保持不变。

## 5. 把续费当成一次单独测试

第一次扣款成功，只能证明第一次扣款成功。

对于循环订阅，至少记录：

- 首次扣款日期
- 预计续费日期
- 含税金额
- 续费前余额
- recurring payment是否仍然开启
- 第一次真实续费结果

只凭signup时成功一次，不要直接说一张卡“续费稳定”。

## 6. 虚拟卡能证明什么，不能证明什么

虚拟卡可以用来：

- 把AI/SaaS支出和主银行卡分开
- 控制余额和风险敞口
- 在普通银行卡不支持时，提供线上/国际/循环付款能力
- 用一张低余额独立卡测试商户

虚拟卡不能证明或保证：

- 账号一定符合资格
- 当前地区一定受支持
- 商户一定接受这个BIN/卡类型
- 续费一定成功
- 能绕过商户或账号侧的风控决定

一张卡在商户A能用，不代表在商户B也能用。

## 7. 找官方support时，给有用的信息

建议带上：

- 产品和付款渠道
- 完整报错
- UTC时间
- 首次付款/续费/invoice上下文
- 银行有没有看到authorization
- invoice/transaction ID（如果有）
- 已经尝试过什么

除非是在官方、已验证的support流程里明确要求，否则不要发送完整卡号、CVV、身份证件或账号密码。

## 8. 什么时候该停止重试

出现这些情况，就别继续刷了，先查原因：

- 完全相同的错误反复出现
- 多次相同提交后，银行仍然完全看不到authorization
- 未付invoice还没解决
- 账号/地区资格不明确
- 身份验证无法完成
- 平台已经明确限制或拒绝该付款/账号

重复点击付款按钮，不是一种排障方法。

## 安全和合规

这个项目只讨论正常订阅和支付故障排查，不建议使用虚假账单资料、虚报居住地、批量养号、滥用chargeback、套现，或尝试绕过平台审核和限制。
